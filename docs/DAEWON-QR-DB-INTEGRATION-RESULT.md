# 대원정밀 MES — QR·입출고·WIP·POP·출하 실제 DB 통합 테스트 결과

> 이 문서에는 접속 정보·비밀번호·키·PIN 값을 적지 않는다. 식별 정보(프로젝트 식별자, 테넌트, 테스트 접두어)만 기록한다.

## 1. 테스트 목적

QR 연동(원자재 LOT 출고 QR, WIP 라벨/POP WIP QR, 완제품 출하 LOT QR)이 **실제 PostgreSQL(Supabase)** 에서 기존 MES 업무 규칙(재고·LOT 추적·수불·작업지시·출하)과 어긋나지 않는지, 그리고 동시 요청·잠금 상황에서 데이터가 일관되게 유지되는지 확인한다. 단위 테스트(가짜 DB)로는 확인할 수 없던 다음을 실제 DB로 확인하는 것이 핵심이다.

- QR로 고른 결과와 수동으로 고른 결과가 같은 서버 규칙·같은 DB 결과를 낳는가
- QR 스캔(조회)만으로 출고·작업 시작·실적 등록·출하 등록/확정·재고 변경이 일어나지 않는가
- `FOR SHARE`/`FOR UPDATE`/`lock_timeout`/교착 방지 순서가 실제 PostgreSQL에서 의도대로 동작하는가

## 3. 테스트 범위

| 구분 | 내용 |
|---|---|
| 원자재 | 입고(멱등 `requestId`), LOT/재고/수불 생성, LOT QR 조회, 수동/QR 자재 출고, 재고 차감, 수불 이력, WIP 생성·연결, 재고 초과·LOT 중복 거부 |
| WIP·POP | WIP 라벨 최초/재발행 이력, 동시 발행, `lock_timeout`, 실제 POP PIN 로그인 세션, 현장/관리자 POP WIP QR 조회, 공정 시작→실적→완료, WIP 이동 이력 |
| 완제품·출하 | 완제품 입고(분할 LOT), 재고, 출하 LOT QR 조회(품목/창고/상태 검증), 출하예정 등록(Multi-LOT·예약), 출하 확정(차감·수불·수주 출하수량) |
| 동시성 | 같은 LOT 동시 출고·출하, LOT 순서가 반대인 출고(교착), `FOR SHARE`와 LOT 상태 변경, 출고와 LOT 격리 경합, 이중 확정 |
| 실제 화면 | 실제 Next 서버(`next build` + `next start`)에서 출하예정 등록 시트와 현장/관리자 POP의 [QR 스캔]. 가짜 카메라(`--use-fake-device-for-media-stream`) + `BarcodeDetector` 모킹 |

## 4. 검증된 업무 흐름

모든 항목은 앱의 **실제 서버 액션**을 호출했고, 상태는 실제 DB에서 다시 읽어 확인했다. (인증은 앱과 같은 JWT 세션 쿠키 / 실제 `popLogin` PIN 로그인으로 구성)

1. **원자재 입고 → LOT/재고/수불**: 입고 4건 → LOT 4, 재고 행, `RECEIPT` 수불. 같은 `requestId` 재전송은 새 LOT 없이 기존 결과 반환.
2. **자재 출고(수동 vs QR)**: 재고 차감량, `ISSUE` 수불 2건, WIP 1건(`WAITING`), 자재 LOT 추적(`WorkOrderMaterialLot`, `WipUnitMaterialLot`), `CREATED` 이동 이력이 두 방식에서 동일.
3. **WIP 라벨**: 최초 `WIP_LABEL_ISSUE`, 재요청은 사유 필수, `WIP_LABEL_REISSUE`. QR payload `DAEWON|WIP|1|<WipUnit.id>` 불변.
4. **POP**: 세션 없음/VIEWER 거부, 현장(PIN)·관리자 세션은 동일한 조회 결과. 조회 전후 WIP·공정·실적·이동·감사 로그 변화 없음(스캔만으로 작업 시작/실적 없음).
5. **공정 처리**: 공정 시작→실적→완료→작업지시 `COMPLETED`, WIP 이동 `CREATED > STARTED > MOVED > STARTED > COMPLETED`.
6. **완제품 입고**: 60 + 40 분할 입고 → LOT 2개(제조번호, 제조번호-01), LOT별 재고, `RECEIPT` 수불.
7. **출하 LOT QR 조회**: 정상 LOT는 수동 목록의 같은 행과 동일. 원자재/다른 품목/없는 LOT/다른 창고/격리/재고 0/잘못된 값/세션 없음은 거부. 조회만으로 등록·확정·재고 변경 없음.
8. **출하예정 등록·확정**: 예약 수량이 가용에 반영, 초과·중복 LOT·격리 LOT 거부, 확정 시 차감·`ISSUE` 수불·수주 출하수량 증가·상태 `PARTIAL_SHIPPED`, 재확정 거부.

## 5. 동시성 테스트 결과

| 시나리오 | 결과 |
|---|---|
| 같은 LOT(100)에 4건×40 동시 출고 | 성공 정확히 2건, 잔량 20, 수불·WIP도 2건. 실패 건은 WIP 미생성(부분 커밋 없음) |
| LOT 순서가 반대인 출고 3라운드 | 교착 0건, 모두 성공, 최종 재고 정확 |
| `FOR SHARE` 끼리 | 비충돌(두 번째 공유 잠금이 약 30ms에 통과) |
| `FOR SHARE` 보유 중 LOT 상태 변경 | 대기 후 1.5초 `lock_timeout`으로 실패, 상태 불변, 잔여 잠금 없음 |
| 출고와 LOT 격리 경합(시차 5가지) | 매번 성공 건수 = 재고 차감 = 수불 = WIP 건수. 격리 확정 후 출고는 거부되고 재고 불변 |
| 같은 WIP 라벨 동시 최초 발행 6건 | 성공 정확히 1건, 이력 1건 |
| 같은 WIP 라벨 동시 재발행 6건 | 발행 횟수 2~7이 중복·결번 없이 기록 |
| WIP 행 잠금 중 라벨 발행 | 약 5.2초 후 `lock_timeout`으로 실패, 이력 없음, 잠금 해제 후 정상 |
| 같은 LOT 동시 출하예정 등록 4건 | 성공 1건, 초과 예약 없음 |
| 같은 출하 동시 확정 4건 | 성공 1건, 이중 차감 없음 |
| 같은 LOT의 다른 출하 2건 동시 확정 | 모두 성공, 합계 정확 |
| 예약 후 LOT 격리 → 확정 / 실재고 부족 확정 | 확정 거부, 출하 `PLANNED` 유지, 롤백. 복구 후 정상 확정 |

음수 재고 행은 전 과정에서 0건이었다. 최대 병렬도는 4~6건이다(부하 테스트가 아님).

## 6. QR 방식과 수동 방식 비교

| 비교 대상 | 결과 |
|---|---|
| 원자재 출고: QR 선택 vs 수동 선택 | 재고 차감, 수불, WIP, 추적 연결 구조 **동일** |
| 출하예정 등록: QR 선택 vs 수동 선택 | LOT·수량·품목·창고·상태 구조 **동일**, 같은 서버 검증 적용 |
| 출하 확정: QR 선택 vs 수동 선택 | 같은 규칙으로 차감, 수불 `ISSUE` 동일 |
| POP WIP 조회: 현장 PIN 세션 vs 관리자 세션 | 결과 **동일** |
| 스캔(조회)만 했을 때 | 재고·작업 상태·실적·출하·감사 로그 **변화 없음** (QR은 선택/조회만 하고, 실행은 기존 버튼의 서버 검증을 거침) |

실제 화면에서도 QR 등록과 수동 등록의 결과 구조가 같았고, QR 스캔 1회는 읽기 전용 조회 Server Action 1건만 발생시켰다(출하 건수 불변).

## 8. 테스트 데이터 식별 규칙(ZT5)

모든 테스트 데이터는 `ZT5` 접두어로 식별한다. 기존 업무 데이터에는 쓰지 않는다.

| 대상 | 식별 |
|---|---|
| 사용자 | `zt5-admin`, `zt5-operator`, `zt5-viewer` (이메일 `*@zt5.test.invalid`, 비밀번호 로그인 불가 해시) |
| 품목 | `ZT5-RM-A`, `ZT5-RM-B`, `ZT5-FG-A`, `ZT5-FG-B` |
| 창고 | `ZT5-WH-RM`, `ZT5-WH-FG`, `ZT5-WH-FG2` (+ 로케이션 `-A01`) |
| 거래처 | `ZT5-SUP`, `ZT5-CUS` |
| BOM / 라우팅 | BOM 버전 `ZT5-1`, 라우팅 `ZT5-RT-A` (공정 `ZT5-OP10`, `ZT5-OP20`) |
| 발주 / 수주 | `ZT5-PO-001`, `ZT5-SO-001` |
| LOT | `ZT5-L-*`, `ZT5-MFG-*`(완제품), `ZT5-UI-*`(화면 테스트) |
| 작업지시 제조번호 | `ZT5-MFG-*` (작업지시 번호는 시스템 채번이라 접두어가 없다 → 품목/제조번호로 식별) |

실행 직후 집계: ZT5 품목 4, 사용자 3, LOT 68, 작업지시 57, WIP 38, 수불 163, 출하 9. 테스트 사용자 `zt5-operator`에는 테스트용 POP PIN이 설정되어 있다(PIN 값은 이 문서에 기록하지 않는다).

**시스템 채번 소비**: 테스트가 실제 채번을 소비했다(작업지시 `WO-2026-001`~`058`, 출하 `SH-2026-001`~`009`). 번호는 ZT5 데이터를 지워도 되돌아가지 않을 수 있으므로 운영 전 채번 시작값을 확인해야 한다.

## 9. 미검증 항목

- 최종검사 불합격/미검사 LOT의 출하 제한: 실제 DB의 검사 이력이 필요해 가짜 DB 단위 테스트로만 확인했다.
- 격리와 출고의 가장 좁은 경합 구간: 시차 5가지(0~600ms)로는 출고 트랜잭션 중간에 정확히 끼어드는 순간을 재현하지 못했다. 모든 시차에서 일관성은 유지됐다.
- 자재 반품, 외주 입출고, 재작업/보류 WIP 흐름.
- 트랜잭션 풀러(6543) 외 다른 접속 구성, Vercel 운영 배포 환경에서의 풀러 거동.
- 대량 동시 접속 부하 테스트(이번 최대 병렬도는 4~6).
- 실제 현장 작업자 계정/PIN, 운영 권한 구성(테스트는 `zt5-*` 사용자 3종으로 수행).

## 10. 현장 장비 테스트 필요사항

- 실제 Android 태블릿 카메라의 LOT/WIP 라벨 인식률, 카메라 권한 요청, 저조도/반사 환경. (이번 화면 테스트는 가짜 카메라와 `BarcodeDetector` 모킹)
- 실제 프린터(Brother)로 인쇄한 라벨의 스캔 가능 여부, 인쇄 크기별 QR 인식.
- 장갑 착용 상태에서 [QR 스캔] 버튼 터치(출하 화면 버튼 높이 36px).
- 현장 POP에서 실제 작업자 PIN 로그인 → WIP 스캔 → 작업 선택 흐름.
- 현장 PC/NCWatch 에이전트가 있는 환경에서의 동작.

## 11. 실제 운영 전 데이터 정리 유의사항

- 이 DB는 테스트 데이터와 **기존 마스터·설비 데이터가 함께** 있다. 운영 전 초기화 시 **기존 품목·BOM·설비 이벤트 데이터를 유지할지 별도로 결정**해야 한다. 이번 스위트는 어떤 데이터도 삭제하지 않으며, DB 전체 초기화나 `prisma migrate reset`은 실행하지 않았다.
- 정리는 `ZT5` 접두어로 대상을 식별한 뒤 외래키 순서에 맞춰 수행한다. 정리 스크립트는 만들지 않았다(아래 항목은 수동 점검 목록).
  - 종속 데이터(작업지시/공정/실적/WIP/이동, 자재 LOT 추적, 수불, 재고, 출하, 감사 로그 중 해당 항목)를 먼저, 마스터(LOT, 품목, BOM, 라우팅, 발주/수주, 창고, 사용자)를 나중에 정리.
  - 작업지시 번호 `WO-2026-*`, 출하번호 `SH-2026-*`는 제조번호/ZT5 품목으로 식별.
  - 사용자 `zt5-*`와 테스트 PIN은 운영 전 반드시 제거(또는 PIN 변경).
- 시스템 채번(작업지시/출하)의 소비분 처리 방침을 정한다.
- 정리 후에는 위 실제 DB 시나리오 중 일부(`00-inspect`, 소규모 입고/출고)로 정상 동작을 확인한다.

## 12. 테스트 스크립트 실행 방법

스크립트는 `scripts/db-it/`에 있다. **`npm test`, `next build`, 배포 과정에서 자동 실행되지 않는다**(`package.json`에 연결하지 않았고, 아래 환경변수를 직접 지정해야만 실행된다).

| 파일 | 역할 |
|---|---|
| `env.ts` | 접속 환경 로드, 대상 검증(`verifyTarget`), 테스트 PIN 환경변수 읽기 |
| `lib.ts` | 하네스: 실제 Prisma, JWT 쿠키 주입(`next/headers`, `next/cache` 대체), 검증 헬퍼, 공통 픽스처 |
| `with-env.js` | 환경을 올린 뒤 명령 실행(실제 화면 테스트용 Next 서버 기동용). 같은 대상 검증 포함 |
| `00-inspect.ts` | **읽기 전용**: 대상·스키마·기존 데이터 점검 |
| `01-seed.ts` | ZT5 사용자/품목/창고/BOM/라우팅/발주/수주 준비(재실행해도 중복 생성 안 함) |
| `02-raw-material.ts` | 원자재 입고/출고/QR |
| `03-wip-pop.ts` | WIP 라벨, POP, 공정 처리 (테스트 PIN 설정) |
| `04-fg-shipment.ts` | 완제품 입고·출하·동시성 |
| `05-issue-concurrency.ts` | 출고 동시성·잠금 |
| `06-ui-prep.ts` / `06-ui-browser.ts` | 실제 화면 출하 테스트(준비 / 실행) |
| `07-pop-ui.ts` | 실제 화면 POP 테스트 |

권장 순서: `00` → `01` → `02` → `03` → `04` → `05` → (`06`·`07`: 실제 Next 서버 필요).

실행 예(Bash). 모든 명령에 필요한 환경변수:

- `DAEWON_DB_IT_CONFIRM=aquqetajewvhyirmewfy` — 실행 확인(없거나 다르면 거부)
- `ZT5_POP_PIN=<테스트 전용 PIN>` — `03`, `04`, `07`에 필요. 값은 코드/문서에 두지 않는다. `03`이 이 값을 `zt5-operator`의 POP PIN으로 설정하므로 `04`, `07`에는 `03`과 같은 값을 사용한다.
- `DAEWON_ENV_FILE=<.env.local 경로>` — 선택. 기본값은 메인 worktree의 `.env.local`

```bash
export DAEWON_DB_IT_CONFIRM=aquqetajewvhyirmewfy
export ZT5_POP_PIN=<테스트용 PIN>
RUN="npx ts-node --compiler-options {\"module\":\"commonjs\"} --project tsconfig.json"

$RUN scripts/db-it/00-inspect.ts          # 읽기 전용 점검
$RUN scripts/db-it/01-seed.ts
$RUN scripts/db-it/02-raw-material.ts
$RUN scripts/db-it/03-wip-pop.ts
$RUN scripts/db-it/04-fg-shipment.ts
$RUN scripts/db-it/05-issue-concurrency.ts
```

실제 화면 테스트(`06`, `07`)는 Next 서버를 같은 DB에 붙여 띄운 뒤 실행한다.

```bash
node scripts/db-it/with-env.js npx next build
node scripts/db-it/with-env.js npx next start -p 3130 &     # 포트는 UI_BASE로 변경 가능
export UIPREP="$($RUN scripts/db-it/06-ui-prep.ts | sed -n 's/^UIPREP //p')"
$RUN scripts/db-it/06-ui-browser.ts
$RUN scripts/db-it/07-pop-ui.ts
```

주의:

- `--transpile-only`를 쓰지 않는다(`moduleResolution: bundler`와 충돌해 TS5095 오류가 난다).
- 반복 실행하면 ZT5 데이터와 채번 소비가 계속 늘어난다.
- 대원정밀 브랜드는 LOT·제조번호 자동채번 규칙이 정책상 없어 입고/작업지시에 번호를 직접 넣어야 한다(스크립트가 처리).
- `OPERATOR` 역할은 `WORK_ORDER` 생성 권한이 없어 스크립트가 작업지시 생성만 `zt5-admin`으로 수행한다.

## 13. 보안 및 DB 연결 주의사항

- **실행 안전장치**(`env.ts` `verifyTarget`, `with-env.js`): 아래를 모두 만족하지 않으면 DB에 접근하기 전에 실행을 거부한다.
  - `DAEWON_DB_IT_CONFIRM`이 대원정밀 프로젝트 식별자와 정확히 같을 것
  - `DATABASE_URL`, `DIRECT_URL`, `NEXT_PUBLIC_SUPABASE_URL`이 모두 같은 프로젝트(`aquqetajewvhyirmewfy`)를 가리킬 것
  - DB 이름이 `postgres`, `DEFAULT_TENANT_ID`가 `daewon-001`일 것
- `lib.ts`를 불러오는 것만으로는(확인 변수가 없으면) 중단된다. 각 시나리오는 `require.main === module`일 때만 실행되므로 import만으로 DB 쓰기가 일어나지 않는다.
- 접속 정보는 저장소 밖의 `.env.local`에서 프로세스 환경변수로만 읽고, 출력하지 않는다. 코드·문서에는 연결 문자열, 키, 비밀번호, PIN이 없다.
- 이 스위트는 **DB 행을 삭제하지 않는다**(`delete`, `deleteMany`, 원시 `DELETE`/`TRUNCATE` 없음). 쓰기는 ZT5 데이터 생성과 앱의 정상 업무 액션 호출, ZT5 LOT 상태/ZT5 재고 행 변경으로 한정된다. 기존 업무·설비 데이터는 건드리지 않는다.
- 테스트 중 `popLogin`이 진단 로그(`[POP_LOGIN_DEBUG]`)를 남긴다(PIN 값은 없고 길이 등만). 기능 문제는 아니나 운영 로그 정책 차원에서 별도 검토 대상이다.
- 다른 프로젝트(다른 회사/MES)로 보이는 대상이 감지되면 실행하지 않는다. 대상이 불분명할 때도 같다.
