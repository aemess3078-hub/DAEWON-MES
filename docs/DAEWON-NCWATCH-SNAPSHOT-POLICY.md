## 1. 코드 분석 (운영 main 기준)

### 1.1 기존 TagSnapshot 저장 조건 (`transform.ts` @35541ce)
`TagCurrentValue` 는 매 수신 upsert, `TagSnapshot` 은 태그마다 **직전 스냅샷 1건을 개별 조회**(`findFirst`)한 뒤 아래 중 하나면 저장했다.
1. 스냅샷이 없을 때, 2. 값이 직전 스냅샷과 다를 때, 3. **마지막 스냅샷으로부터 `NCWATCH_SNAPSHOT_INTERVAL_MS`(기본 60초) 경과**.

- 동일 값 반복 저장: **있음** — 3번 때문에 값이 그대로여도 분당 1건 **[실측]** (설비 4대 × 값이 있는 태그 14개 = 56건/분. 25분간 1,330행 증가)
- 원본 TIMESTAMP 영향: 값 비교에는 쓰이지 않지만, 경과 시간 계산의 기준이 NCWatch 데이터 시각이다. 오프라인에서도 NCWatch 행 시각이 계속 바뀌므로 정기 저장이 계속 발생한다. (시각만 바뀐 것을 "값 변경"으로 보지는 않음 — 값 비교는 문자열 값만 사용)
- `TagCurrentValue` UPDATE 빈도: 수신 1회당 값이 있는 태그 전부(14개/설비). Agent 변경 감지(60초 재전송) 이후 설비당 분당 14회 **[추정, 코드]**

### 1.2 API별 DB 호출 (코드 기반 **[추정]**)
| API | 호출 | 조회 | 쓰기 |
|---|---|---|---|
| `POST heartbeat` | 30초마다 (2,880/일) | 인증 1 | Gateway update 1 |
| `POST status` (설비 N대 포함) | 설비 값 변경 시 10초, 변경 없으면 60초 | 인증 1 + 설비당 **18** (상태 1, 매핑 1, 열린 이벤트 1, 태그+현재값 1, **스냅샷 개별 조회 14**) | 설비당 **15** (상태 upsert 1 + 현재값 14) + 스냅샷 + 변경 시 이력·이벤트 |
| `POST report-daily` | 1시간 | 인증 1 + 설비당 매핑 1 | 설비당 upsert 1 |
| SyncLog | 정상 반복 5분 제한 | – | 5분마다 N+1행 |

STATUS 한 번에 DB 가 읽고 쓰는 데이터량 **[추정]**: 설비당 읽기 ≈ 4~5 KB(태그 15행+현재값, 스냅샷 14행, 상태·매핑), 쓰기 ≈ `ncwatch_status` 1행(평균 768 B, rawPayload 546 B 포함 **[실측]**) + 현재값 14행.

### 1.3 TagSnapshot 을 읽는 곳
| 위치 | 용도 | 영향 |
|---|---|---|
| `getEquipmentMonitorLive` (모니터링 화면 30초 폴링·키오스크) | **TagCurrentValue 사용.** 현재값이 없는 태그에 한해 최신 스냅샷을 폴백(`DISTINCT ON`) | 없음 |
| `getEquipmentMonitorData` (스키마 호환 오류 시 폴백 경로) | 태그별 **최신 스냅샷**을 표시값으로 사용 | 값은 변경 즉시 저장되므로 동일, 값 시각이 최대 15분 늦을 수 있음 |
| `deleteTag`/연결 삭제 | 해당 태그 스냅샷 삭제 | 저장량이 적을수록 빠름 |
| 그 외(품질·분석·통계) | **없음** — 이상·알람·가동 통계는 `EquipmentEvent`/`NcwatchReportDaily` 사용, 시계열 차트 없음 | 없음 |

⇒ 현재 TagSnapshot 은 **읽는 화면이 거의 없는 이력 저장소**(향후 추이 분석용). 값 변경 이력은 보존하고, 동일 값은 15분 간격으로 "살아 있음"만 남기는 정책이 사용 목적을 훼손하지 않는다.

### 1.4 무제한 조회 / N+1 점검
- ⚠️ **[실측] 잠재 위험**: `getEquipmentMonitorData` 의 `snapshots: { orderBy, take: 1 }` 중첩 조회는 Prisma 가 `WHERE tagId IN (…) ORDER BY timestamp DESC OFFSET` 로 **LIMIT 없이 전체 이력을 가져온 뒤 메모리에서 1건만 취한다**(Prisma 쿼리 로그로 확인). 현재는 폴백 경로에서만 호출되어 운영 부하가 없지만, 스냅샷이 쌓인 상태에서 폴백이 발동하면 DB→서버 egress 가 급증할 수 있다. **이 브랜치에서는 수정하지 않았다**(모니터링 코드 변경이라 별도 승인 필요) — 수정안: `getLatestSnapshotFallbacks` 와 같은 `DISTINCT ON` 조회로 교체.
- 수신 경로 N+1: **개선됨** — 태그별 `tagSnapshot.findFirst` 14회 → 필요할 때만 `groupBy` 1회(캐시 사용).
- 관리 화면 `getNcwatchMappings`: 이력·로그 `take: 1000` 으로 상한 있음(관리자 화면 한정).

## 2. 개선 정책 (구현 내용: `src/lib/ncwatch/transform.ts`)

| 항목 | 정책 |
|---|---|
| STATUS 수집 주기 | 유지 (Agent 변경 없음) |
| `TagCurrentValue` | 유지 — 수신마다 갱신(값·시각이 완전히 같을 때만 쓰기 생략) |
| `EquipmentEvent` / `NcwatchStatusHistory` | 유지 — 상태 변경 즉시, 중복 방지 |
| **TagSnapshot: 값 변경** | **즉시 저장** (비교는 문자열 값만 — 원본 TIMESTAMP·ALIVECOUNT 는 값 변경 아님) |
| **TagSnapshot: 값 동일** | **정기 스냅샷 최대 15분 간격**(`NCWATCH_SNAPSHOT_INTERVAL_MS`, 기본 900000) |
| 스냅샷 판단 조회 | 설비당 태그 14회 개별 조회 → 필요할 때만 1회(`groupBy`) + 인스턴스 메모리 캐시. 캐시는 오래될 수는 있어도 앞설 수 없어 누락이 없고, 저장 직전 DB 값을 재확인해 다중 인스턴스 중복을 막는다 |
| 스냅샷 저장 | 설비 1회 수신에서 여러 개면 `createMany` 1회 |
| 알람 해제 처리(부수 수정) | NCWatch 가 알람 필드를 비우면 기존에는 `ALARM_*` 태그가 **알람 문구를 그대로 유지**했다. 이제 빈 값으로 갱신+스냅샷. (오프라인 시 들어 있던 "Offline" 문구도 가동 전환 시 정리됨) |
| 환경변수 파싱 | 빈 문자열 등 비숫자는 기본값 사용 (기존: `NaN` 이 되어 정기 저장이 영구 중단될 수 있었음) |
| **선택 정책(기본 꺼짐)** | `NCWATCH_SNAPSHOT_VOLATILE_MIN_INTERVAL_MS`(예 60000): 위치·회전수·이송·진행률·블록번호 7개 "변동 태그"는 변경 스냅샷도 최소 간격을 둔다. STATUS·프로그램·모드·수량·공구·알람 같은 이산 태그는 항상 즉시 |

CNC-1: 연결 대기 중에도 수집·매핑·스냅샷 대상 그대로(정기 스냅샷 포함). 스키마·기존 데이터 변경 없음, Agent 변경 없음.

## 3. 저장량 · 비용 분석

### 3.1 DB 저장 건수 (TagSnapshot)
| 시나리오 | 개선 전 | 개선 후(기본) | 개선 후 + 변동 태그 60초 제한(선택) |
|---|---|---|---|
| **전 설비 OFFLINE/정지 유지** (4대 × 14태그) | **80,640/일, 2,419,200/30일** [실측 속도 기반] | **5,376/일, 161,280/30일 (−93.3%)** [코드 계산, 테스트로 15분 간격 확인] | 동일 |
| **4대 24시간 가동, 변동 태그 7개가 10초마다 변화(상한)** | ≈ 241,920/일 + 이산 변경 [추정] ≈ 7.3M/30일 | **개선 전과 동일** (값이 바뀌므로 즉시 저장 정책 그대로) | ≈ 40,320/일 ≈ 1.2M/30일 (−83%) |
| 하루 8시간 가동 + 16시간 정지(예시) | ≈ 80,640×(16/24) + 241,920×(8/24) ≈ 134,400/일 [추정] | ≈ 3,584 + 80,640 ≈ 84,200/일 (−37%) | ≈ 3,584 + 13,440 ≈ 17,000/일 (−87%) |

> **핵심**: 요청하신 정책(변경 즉시 + 동일 값 15분)은 **정지·오프라인 구간**을 93% 줄이지만, **가동 중 계속 변하는 위치·회전수** 때문에 가동 시간이 길수록 효과가 작아진다. 가동 중 저장량을 억제하려면 선택 정책(60초 제한)이 필요하다 — 결정이 필요하다.

행 크기 **[실측]**: 스냅샷 행 평균 97 B + 인덱스 포함 실제 점유 약 250~320 B/행(1,330행 = 416 KB). 80,640행/일 ≈ 20~26 MB/일 ≈ **0.6~0.8 GB/30일** → 개선 후 0.04~0.05 GB/30일 [추정]. DB 용량 상한(Free 500 MB 여부 등)은 Supabase 플랜 확인 ⛔.

## 4. 테스트 (`npm run test:ncwatch-phase12`, **117 단언 PASS**)

6. Agent 재시작(동일 행 재전송·시각만 다른 값·서버 캐시 소실) → 중복 0건 ✅

8. 14분 59초 → 없음 / 15분 → 정확히 1건 / 직후 재저장 없음 ✅
9. 4대 동시 수신 → 설비별 독립 저장, 한 설비 변경 시 1건만 ✅
10. 중복 이벤트 방지 → 설비당 이벤트·열린 이벤트 1건 유지 ✅
